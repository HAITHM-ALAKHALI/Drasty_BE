# دليل هيكلية وفحوص Drasty للفريق

## مقدمة

يهدف هذا الدليل إلى مساعدة أعضاء فريق Drasty على فهم ملفات الاختبار التي أُنشئت للمشروع، وطريقة تشغيلها، والفرق بين اختبارات Feature وUnit، وما الذي يغطيه كل اختبار بالنسبة إلى جداول قاعدة البيانات ومسارات API.

لا يهدف الدليل إلى شرح كل تفاصيل Laravel، بل يركز على ما يحتاجه الفريق لفهم مجموعة الفحوص الحالية وقراءتها وتشغيلها والمحافظة عليها.

# الفصل الأول: هيكلية ملف الاختبار ومتطلبات التشغيل

## 1.1 موقع ملفات الاختبار

يحتوي المشروع على مجلدين أساسيين للاختبارات:

```text
tests/
├── Feature/
└── Unit/
```

يُستخدم مجلد `Feature` للاختبارات التي تمر عبر مسار التطبيق، مثل Route وController وModel وقاعدة البيانات. أما مجلد `Unit` فيُستخدم لاختبار وحدة صغيرة مستقلة دون الحاجة إلى HTTP أو قاعدة البيانات.

توجد ملفات اختبارات API الحالية في:

```text
E:\projects\Drasty\tests\Feature
```

وتوجد اختبارات خدمة `SystemSettings` في:

```text
E:\projects\Drasty\tests\Unit\SystemSettingsTest.php
```

## 1.2 بنية ملف Feature Test

يتكون ملف Feature Test النموذجي من مساحة أسماء، واستيرادات، وصنف يرث من `Tests\TestCase`، ثم دوال اختبار عامة تبدأ أسماؤها غالبًا بـ `test_`.

مثال مبسط:

```php
<?php

namespace Tests\Feature;

use Illuminate\Support\Facades\DB;
use Tests\TestCase;

class CourseApiTest extends TestCase
{
    public function test_courses_endpoint_returns_courses(): void
    {
        // Arrange
        $databaseCount = DB::table('courses')->count();

        // Act
        $response = $this->getJson('/api/courses');

        // Assert
        $response->assertStatus(200);
        $response->assertJsonPath('status', true);
        $response->assertJsonPath('count', $databaseCount);
    }
}
```

## 1.3 معنى عناصر الملف

يشير السطر `namespace Tests\Feature;` إلى أن الملف ينتمي إلى مساحة أسماء اختبارات Feature. ويسمح السطر `use Tests\TestCase;` باستخدام إمكانيات Laravel المخصصة للاختبارات.

عندما يرث الصنف من `TestCase`، يستطيع استخدام دوال مثل `getJson` و`postJson` و`putJson` و`deleteJson`، إضافة إلى دوال التحقق مثل `assertStatus` و`assertJsonStructure` و`assertDatabaseHas`.

يكتشف PHPUnit دالة الاختبار لأنها عامة ويحمل اسمها بادئة `test_`. ويمكن أيضًا استخدام Attribute خاص بـ PHPUnit، لكن ملفات المشروع الحالية تعتمد أسلوب الاسم.

## 1.4 تنظيم الاختبار بأسلوب AAA

تتكون الفحوص من ثلاث مراحل:

### Arrange

في هذه المرحلة نجهز المدخلات أو نقرأ البيانات المطلوبة قبل العملية. مثال:

```php
$databaseCount = DB::table('courses')->count();
```

### Act

في هذه المرحلة ننفذ العملية التي نريد فحصها:

```php
$response = $this->getJson('/api/courses');
```

### Assert

في هذه المرحلة نتحقق من النتيجة:

```php
$response->assertStatus(200);
$response->assertJsonPath('status', true);
```

يساعد هذا التنظيم على معرفة ما الذي جهزناه، وما الذي نفذناه، وما النتيجة التي توقعناها.

## 1.5 دوال HTTP المستخدمة

| الدالة | العملية التي تمثلها | مثال |
|---|---|---|
| `getJson` | قراءة بيانات | `getJson('/api/courses')` |
| `postJson` | إنشاء سجل أو إرسال بيانات | `postJson('/api/courses', $data)` |
| `putJson` | تعديل سجل | `putJson('/api/courses/1', $data)` |
| `deleteJson` | حذف سجل | `deleteJson('/api/courses/1')` |

هذه الطلبات داخلية. فهي لا تحتاج إلى فتح المتصفح أو تشغيل Postman، لكنها تمر عبر Route وController وطبقات Laravel كما يمر الطلب الحقيقي.

## 1.6 دوال التحقق المستخدمة

تتحقق `assertStatus(200)` من حالة HTTP. وتتحقق `assertJsonStructure` من وجود مفاتيح JSON المطلوبة. أما `assertJsonPath` فتتحقق من قيمة موجودة في مسار محدد داخل JSON.

تتحقق `assertJsonFragment` من وجود مجموعة قيم داخل الاستجابة دون اشتراط مطابقة الاستجابة كاملة. وتتحقق `assertDatabaseHas` من وجود سجل في قاعدة البيانات. في المقابل، تتحقق `assertDatabaseMissing` من عدم وجود سجل.

مثال:

```php
$this->assertDatabaseHas('courses', [
    'course_id' => $courseId,
]);
```

## 1.7 اختبار قاعدة البيانات الحالية

تم ضبط `phpunit.xml` لاستخدام اتصال MySQL المحلي وقاعدة `darasty_db_2`. لذلك تقرأ اختبارات Feature البيانات من قاعدة البيانات التي يعمل عليها المشروع.

لا تستخدم المجموعة الحالية `RefreshDatabase`، ولا تنفذ `migrate:fresh` أو `migrate:refresh` أثناء تشغيل هذه الاختبارات. السبب هو أن هذه الأوامر قد تحذف الجداول أو البيانات.

تستخدم اختبارات الإنشاء بيانات مؤقتة ذات رموز فريدة، ثم تحذفها داخل `finally`. يضمن `finally` تنفيذ التنظيف حتى إذا فشل أحد التحققات بعد إنشاء السجل.

## 1.8 متطلبات التشغيل السليم

يتطلب تشغيل الفحوص ما يأتي:

1. فتح المشروع من المسار:

```text
E:\projects\Drasty
```

2. تشغيل MySQL من XAMPP.
3. وجود قاعدة البيانات `darasty_db_2` واستيراد ملف SQL إليها.
4. وجود ملف `.env` بإعدادات MySQL الصحيحة.
5. وجود مجلد `vendor` وحزم Composer.
6. عمل أمر `php artisan --version`.
7. تفعيل امتداد PHP `intl`، وهو مطلوب لبعض أوامر Laravel الخاصة بالعرض والتنسيق.
8. تشغيل الاختبار من Terminal داخل مجلد المشروع.

## 1.9 أوامر التشغيل

لتشغيل ملف واحد:

```cmd
php artisan test tests/Feature/CourseApiTest.php
```

لتشغيل اختبار Unit:

```cmd
php artisan test tests/Unit/SystemSettingsTest.php
```

لتشغيل اختبار محدد بالاسم:

```cmd
php artisan test --filter=test_courses_endpoint_returns_courses
```

لتشغيل جميع الاختبارات:

```cmd
php artisan test
```

## 1.10 بنية Unit Test لخدمة SystemSettings

ملف `SystemSettingsTest.php` يختلف عن ملفات Feature؛ لأنه لا يرسل طلبات HTTP ولا يقرأ قاعدة البيانات. إنه يختبر كلاسًا مستقلًا في:

```text
app/Services/SystemSettings.php
```

ويختبر `getInstance` و`get` و`set` و`getAll` و`__wakeup`.

لأن `SystemSettings` يستخدم Singleton، توجد خاصية ساكنة تحفظ النسخة الوحيدة. استخدم ملف الاختبار Reflection للوصول إلى الخاصية الخاصة وإعادتها إلى `null` في `setUp` و`tearDown`. هذا يمنع أن يغير اختبار إعدادًا ثم يؤثر في اختبار آخر.

## 1.11 الفرق بين Feature وUnit في المشروع

يختبر Feature Test مسارًا متكاملًا يبدأ من HTTP وينتهي باستجابة JSON أو تغيير في قاعدة البيانات. أما Unit Test فيختبر وحدة صغيرة بمعزل عن بقية النظام. لذلك لا يحتاج Unit Test الخاص بـ`SystemSettings` إلى XAMPP أو قاعدة MySQL، بينما تحتاج اختبارات API الحالية إلى اتصال قاعدة البيانات.

# الفصل الثاني: الفحوص المطبقة على كل جدول

## 2.1 جدول الأقسام `departments`

يُعرض جدول الأقسام من خلال المسار `GET /api/departments`. تحقق الاختبارات من نجاح القراءة، ومن بنية JSON، ومن تطابق عدد النتائج مع عدد السجلات في الجدول، ومن وجود قسم معروف.

كما أُعد اختبار إنشاء قسم مؤقت؛ إذ يرسل بيانات اسم ورمز فريدين، ويتحقق من عودة `201` ووجود السجل، ثم يحذفه بعد الاختبار. يغطي ذلك عملية الإضافة دون ترك بيانات اختبارية دائمة.

## 2.2 جدول المستويات `levels`

يُختبر المسار `GET /api/levels`. تتحقق الفحوص من مفاتيح المستوى، ومن بيانات القسم المرتبط به، مثل `department_name` و`department_code`، ومن مطابقة العدد لقاعدة البيانات.

لاختبار العلاقة، تعتمد الاستجابة على ربط كل مستوى بقسمه. لذلك فإن نجاح بنية الاستجابة يثبت أن المسار استطاع تحميل العلاقة المطلوبة وإعادة بياناتها.

## 2.3 جدول الفصول الدراسية `semesters`

يُختبر المسار العام `GET /api/semesters`، كما تُختبر الفلترة باستخدام:

```text
GET /api/semesters?level_id=1
```

يتحقق اختبار الفلترة من أن عدد النتائج يطابق عدد سجلات المستوى المطلوب، ثم يفحص كل نتيجة للتأكد من أن `level_id` يساوي القيمة المطلوبة.

## 2.4 جدول المواد `courses`

يحتوي ملف المواد على المجموعة الأوسع من الفحوص. تشمل الفحوص قراءة المواد، والتحقق من بنيتها، والتحقق من ترتيبها حسب `course_name_ar`، ورفض الطلب الذي يفتقد الحقول الإلزامية، ورفض رمز مادة مكرر.

كما اختُبر إنشاء مادة مؤقتة بنجاح، ثم اختُبر تعديل مادة غير موجودة وإرجاع `404`. واختُبر منع حذف مادة مرتبطة بعرض دراسي وإرجاع `409`. وأخيرًا اختُبر حذف مادة مؤقتة غير مرتبطة بنجاح.

أثناء اختبار التعديل الناجح ظهر أن Controller يستخدم في قاعدة التحقق العمود `name`، بينما يحتوي الجدول على `course_name_ar`. وبما أن قرار الفريق هو عدم تعديل Backend في هذه المرحلة، تم توثيق السلوك الحالي كحالة `500` بدل اعتبار التعديل الناجح وظيفة مكتملة.

## 2.5 جدول الدكاترة `doctors`

يُختبر المسار `GET /api/doctors`. يعيد المسار بيانات الدكتور مع المستخدم المرتبط به. تتحقق الفحوص من البنية، ومن العدد، ومن أن `user_id` لكل دكتور موجود في جدول `users`، وأن المستخدم الموجود داخل JSON هو المستخدم نفسه المرتبط بالدكتور.

## 2.6 جدول المستخدمين `users`

لم يُختبر جدول المستخدمين بوصفه مورد قراءة مستقلًا في المجموعة الحالية، لكنه اختُبر بصورة تكاملية من خلال علاقة الدكاترة بالمستخدمين. فالاختبار يتحقق من وجود `user_id` في جدول `users` ومن تطابقه مع العلاقة المعادة.

## 2.7 جدول أنواع المحتوى `content_types`

يُختبر المسار `GET /api/content-types`. تتحقق الفحوص من بنية العناصر وعددها، ثم تتحقق من وجود نوع المحتوى «محاضرة» مع المعرف والوصف المتوقعين.

## 2.8 جدول عروض المواد `course_offerings`

يُختبر المسار `GET /api/course-offerings`. تتحقق الفحوص من بيانات العرض والمادة والفصل والدكاترة المرتبطين به. كما تُختبر الفلترة حسب `semester_id`، ويتحقق الاختبار من أن كل عرض معاد يرتبط بالفصل المطلوب فعليًا في قاعدة البيانات.

## 2.9 جدول تعيين الدكاترة `course_doctors`

يُختبر المسار `GET /api/course-doctors`. تتحقق الفحوص من بيانات التعيين والمادة والدكتور والقسم والمستوى والفصل. كما تتحقق من أن كل `course_doctor_id` معاد من API موجود فعلًا في جدول `course_doctors`.

## 2.10 الجداول والعلاقات التي لم تُغطَّ بصورة كاملة

لم تُغطَّ جميع عمليات المصادقة والأدوار ومسارات الموظفين ورفع المحتوى والتخزين الخارجي. كما لم تُغطَّ كل حالات التعديل والحذف لكل جدول، لأن الهدف كان تطبيق نمط فحص معياري على الموارد الأكاديمية الأساسية بدل تكرار المجموعة نفسها بصورة كاملة لكل جدول.

## 2.11 كيف يشرح الفريق الفحوص في المناقشة

يمكن وصف العمل بالطريقة الآتية:

> اختبر الفريق مسارات القراءة الأساسية لجميع الموارد الأكاديمية، ثم اختار نماذج ممثلة لعمليات الإنشاء والتحقق والتعديل والحذف والعلاقات المرجعية. استخدمت الاختبارات Laravel Feature Testing مع قاعدة MySQL المحلية، بينما خُصصت اختبارات Unit للكلاسات المستقلة مثل `SystemSettings`. وقد صُممت اختبارات العمليات التي تغير البيانات باستخدام سجلات مؤقتة مع تنظيفها بعد التنفيذ.

## 2.12 قراءة نتيجة الاختبار

تعني كلمة `PASS` أن جميع التحققات داخل الاختبار نجحت. أما `FAIL` فتعني أن نتيجة فعلية اختلفت عن النتيجة المتوقعة. يجب قراءة رسالة الخطأ واسم الملف ورقم السطر قبل تغيير الاختبار.

إذا كشف الاختبار خطأ في Backend، فلا ينبغي تغيير القيمة المتوقعة فقط لإجبار الاختبار على النجاح. يجب أولًا تحديد ما إذا كان السلوك الفعلي يمثل السلوك المطلوب. في حالة تعديل المادة، تم توثيق الخطأ بدل إخفائه.
